# 障害報告書 #002：CPU使用率の高騰

## サマリー
サーバーのCPU使用率が閾値（80%）を継続的に超過し、リソース監視により検知。
HighCpuUsage アラートが設計どおり発報し、負荷の停止により回復した。
本件は監視基盤の動作検証を目的とした計画的な負荷試験である。

## 基本情報
| 項目 | 内容 |
|---|---|
| インシデントID | INC-002 |
| 発生日 | 2026-07-15 |
| 重要度 | Warning |
| 検知方法 | Prometheus リソース監視（Node Exporter） |
| 発報アラート | HighCpuUsage |
| ステータス | 復旧済み |

## 監視値の推移
| タイミング | CPU使用率 |
|---|---|
| 平常時 | 約 0.8% |
| 負荷試験ピーク時 | 約 82% |
| 回復後 | 約 6% |

## タイムライン
| 時刻 | 出来事 |
|---|---|
| （16:00） | stress コマンドで14コアに負荷を投入（障害発生） |
| （16:01） | CPU使用率が80%を超過、HighCpuUsage が PENDING に遷移 |
| （16:06） | 80%超過が5分継続し、PENDING → FIRING に遷移、Alertmanager へ通知 |
| （16:07） | timeout により負荷が自動停止（復旧） |
| （16:07） | CPU使用率が平常値へ回復、アラートが Inactive へ戻る |

## 影響
- 影響範囲：監視対象サーバー（ホスト全体）
- 影響内容：CPUリソースの逼迫。継続した場合、サービスの応答遅延や処理能力低下につながる恐れがある
- 継続時間：約7分（負荷試験の設定時間）

## 根本原因
CPUに対する高負荷（14コアへの継続的な演算負荷）により、使用率が閾値を超過した。
（今回は検証目的で意図的に `stress --cpu 14 --timeout 420` を実行した）

## 対応内容
1. Prometheus の Alerts 画面で HighCpuUsage の PENDING → FIRING 遷移を確認
2. Alertmanager への通知到達を確認
3. 負荷の自動停止（timeout）により使用率が回復
4. CPU使用率の平常値への回復およびアラートの解消を確認

## 検知が機能した点（良かった点）
- リソース監視により、CPU使用率の異常な上昇を数値として捉えられた
- `for: 5m` の設定により、瞬間的な負荷ではなく継続的な高負荷のみを発報対象とする設計が機能した
- severity を warning とした設計により、即時対応が不要なリソース逼迫として適切に分類された

## 考察：サービス停止（#001）との性質の違い
本件は #001 のサービス停止とは異なる性質の障害である。
- #001 は「応答の有無」という二値的な障害であり、for を1分と短く設定した
- #002 は「使用率の連続的な変化」であり、瞬間的な高騰は正常なため for を5分と長く設定した
このように、障害の性質に応じて検知の猶予時間（for）を変えることが、誤報を抑えつつ実障害を捉える鍵となる。

## 再発防止・改善案
- 恒常的にCPU使用率が高い場合は、処理の分散やスケールアップ（リソース増強）を検討する
- 今後の改善：CPU使用率の推移を Grafana でダッシュボード化し、傾向を可視化することで予兆を早期に把握する
- 今後の改善：特定プロセスによる高負荷を切り分けられるよう、プロセス単位の監視追加を検討する
