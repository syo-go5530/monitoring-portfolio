# 監視設計書

## 1. 監視の目的
本監視基盤は、Webサービスの可用性とサーバーリソースを継続的に監視し、
異常を早期に検知することを目的とする。
監視は「サービスが正常に応答するか（外形）」と
「サーバーに十分な余力があるか（リソース）」の両面から行う。

## 2. 監視の3本柱
| 種別 | 監視内容 | 使用コンポーネント |
|---|---|---|
| 死活監視 | サービスが生きているか | Blackbox Exporter |
| 外形監視 | ユーザー目線でHTTP応答が正常か | Blackbox Exporter |
| リソース監視 | CPU/メモリ/ディスクに余力があるか | Node Exporter |

## 3. データ収集の方針
- Prometheus がプル型（自ら取得しに行く方式）で15秒ごとに収集
- 収集間隔15秒は、検知の速さと監視対象・Prometheus双方の負荷のバランスを考慮した標準値

## 4. アラート設計と閾値の根拠

### 4-1. severity（深刻度）の区分
| severity | 意味 | 対応方針 |
|---|---|---|
| critical | サービス停止など即時対応が必要 | 即時対応（実務では時間外でも対応） |
| warning | 放置すると障害につながる予兆 | 翌営業日など計画的に対応 |

### 4-2. 各アラートの設計根拠

| アラート | 閾値 | for | severity | 根拠 |
|---|---|---|---|---|
| WebServiceDown | probe_success == 0 | 1m | critical | サービス停止はユーザーに直接影響し売上に直結するため最優先。瞬断による誤報を避けつつ、検知は極力早くするため for は短めの1分 |
| TargetDown | up == 0 | 2m | critical | 監視対象と通信不能な状態。監視自体の異常も含むため重大。監視系の一時的な取りこぼしで騒がないよう for は2分 |
| HighCpuUsage | > 80% | 5m | warning | CPUは瞬間的に100%になるのは正常。継続的な高負荷のみを問題とするため for は5分。80%は余力を残しつつ予兆を捉えるライン |
| HighMemoryUsage | > 85% | 5m | warning | Linuxはキャッシュでメモリ使用率が高く見えるため、実使用量（MemAvailable基準）で判定。閾値はCPUより高めの85% |
| LowDiskSpace | < 20% | 5m | warning | ディスクは満杯でサービス即死かつ自然回復しない。20%で準備を促す第一段階 |
| CriticalDiskSpace | < 10% | 1m | critical | ディスク枯渇が目前。即時対応が必要なため for を1分に短縮した第二段階 |

## 5. ディスク監視を2段階にした理由
ディスクは他のリソースと異なる性質を持つため、warning と critical の2段階で設計した。

- **満杯になると即座にサービスが停止する**（CPUやメモリは負荷が去れば回復するが、ディスクは回復しない）
- **自然回復しない**（誰かが手動で不要ファイルを削除しない限り空かない）
- **増加傾向が予測可能**（早期に気づけば余裕を持って対処できる）

このため「20%で準備を促し、10%で即時対応を求める」という段階的な設計とした。

## 6. 今後の改善方針
- 各閾値は一般的な初期値であり、実運用でのアラート発生状況を見ながらチューニングする前提
- Alertmanager から Slack 等への通知連携を追加し、検知から通知までを自動化する
- サービスごとの特性（バッチ処理・決済など）に応じた閾値の個別最適化を検討する
